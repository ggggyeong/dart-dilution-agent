# 1단계: 공시 감지와 제목 분류

DART 주요사항보고서(B001) 공시 목록에서 **유상증자·전환사채(CB) 결정 공시를 정확히 골라내는 분류 코드**를 만들고 두 가지 방법으로 검증했다.

- 기준일: 2026-10-15
- 분류 코드 버전: `title-v1`

## 1. 목적과 범위

- B001 공시를 제목과 회사 구분에 상관없이 전부 모으고, 그중 유상증자·CB를 골라낸다.
- 분석할지, 보류할지, 버릴지(상장 여부, 납입 방식 등)는 이 단계에서 정하지 않는다. 다음 단계의 일이다.
- 수집 기간은 2023-04-16 ~ 2026-10-15(3년 6개월)이다.
  - 분석 구간은 2023-10-16 이후이다.
  - 앞 6개월은 정정본의 원본을 찾기 위한 여유분이다.

## 2. 실제 흐름에서 쓰는 DART API

| API | 주는 것 | 역할 |
|---|---|---|
| ① 목록 API (`list.json`) | 공시 제목, 접수번호, 회사, 날짜 | **감지 + 제목 분류** (이 단계) |
| ② 원문 API (`document.xml`) | 공시 원문 XML. 칸마다 코드(`ACODE`)가 붙어 있음 | **숫자 추출** (다음 작업) |
| ③ 전용 API (`piicDecsn`, `pifricDecsn`, `cvbdIsDecsn`) | 유상증자·CB 일부 항목을 정리한 JSON | **검증용으로만** 사용 |

전용 API(③)를 메인 흐름에 쓰지 않는 이유:
- 회사 코드를 넣어야 조회할 수 있어서 새 공시를 감지할 수 없다.
- 사건마다 최종본 1건만 준다 (시범 호출로 확인).
- 유상증자 발행가와 할인율 칸이 없다 (시범 호출의 응답 칸 목록으로 확인).

## 3. 분류 코드 설계

[`classify/report_title.py`](../src/filingscope/classify/report_title.py)

| 규칙 | 내용 |
|---|---|
| 정정 태그 | 제목 앞 `[ ]` 태그(기재정정, 첨부정정, 첨부추가, 정정명령부과 등)가 있으면 `is_correction=true`. 태그 원문은 `report_tag`에 저장하고, 여러 개면 쉼표로 잇는다 |
| 띄어쓰기 | 지우고 비교한다 ("전환사채권 발행결정"도 CB) |
| 유상증자 | 제목에 "유상증자결정"이 있으면 유상증자. "유무상증자결정"은 유상증자 + `is_mixed=true`. "유무상"에는 "유상증자결정"이 연속된 글자로 없어서 따로 검사한다 |
| CB | `전환사채권?발행결정`. '권'은 있어도 되고 없어도 된다 |
| 그 외 | none (무상증자, 교환사채, 신주인수권부사채, 자기전환사채 매도·취득 등) |

**판정 저장 방식**
- 판정은 제목만으로 정해지므로 **제목 종류마다 한 번** 판정해 `title_classifications` 표에 저장한다.
- 판정할 때마다 분류 코드 버전(`classifier_version`)도 함께 기록한다.
- `title_filings` 뷰는 B001 전체(`b001_filings`) 중 유상증자·CB만 보여준다. 분류 코드를 고친 뒤 `scripts/classify_titles.py`를 다시 실행하면 API 호출 없이 바로 반영된다.

## 4. 검증 1: LLM 정답표

**방법**
- B001 제목 종류 217개를 Claude Opus 5.5에 하나씩 판정시켜 정답표 [`tests/fixtures/title_cases.csv`](../tests/fixtures/title_cases.csv)를 만들었다.
- LLM에는 **제목과 판정 기준만** 주고, 코드의 판정 결과는 보여주지 않았다.
- 출력은 정해진 JSON 형식으로 강제하고 Pydantic으로 검증했다. 제목마다 판정 이유를 한 줄씩 받았다.
- 애매한 제목은 `unsure`로 표시하게 했고, 그 제목은 사람이 정답을 정했다.
- 정답표 테스트는 항상 통과해야 한다 (`tests/test_report_title.py`).

**결과**
- 비용: 입력 184,209 토큰, 출력 19,911 토큰, **약 $1.14**
- 분류 코드와 정답표 비교: **216 / 216 일치** (첫 실행부터)
- unsure 1개("수증", 3건)는 사람이 none으로 확정했다.
- 처음부터 100%가 나와서, 코드와 LLM이 같은 실수를 했을 가능성을 점검했다.
  - 유상증자·CB 20종과, "증자"·"사채"가 들어가지만 대상이 아닌 14종을 따로 검토했다.
  - 이후 사람이 217줄 전체를 검토했고 모두 맞았다.

## 5. 검증 2: DART 전용 API 크로스체크

**방법**
- 대상 회사
  - A: 우리 판정에서 유상증자·CB가 나온 회사 전부 (1,682곳)
  - B: 판정이 없는 코스피·코스닥 상장사 중 무작위 300곳 (시드 42)
- 회사마다 전용 API 3개를 호출해 접수번호 기준으로 양방향 비교했다.
- API는 사건마다 최종본만 주므로, 우리 쪽 원본과 앞선 정정본은 "같은 회사·같은 종류의 더 나중 최종본이 API에 있으면 정상"으로 봤다.

**결과**: 호출 5,946번, 실패 0

| 방향 | 결과 |
|---|---|
| API → 우리 (놓친 것) | API 공시 3,664건(유상 2,098, 유무상 38, CB 1,528) **모두 일치. 놓친 것 0, 종류 다름 0** |
| B그룹 300곳 | API 공시 0건. 판정이 없는 상장사에서 놓친 것 없음 |
| 우리 → API (A그룹 11,884건) | 접수번호 그대로 일치 3,664, 더 나중 최종본이 있음 6,877, **API에 최종본 없음 1,343** |

**API에 최종본이 없는 1,343건의 원인**

| 원인 | 건수 | 확인 상태 |
|---|---|---|
| "주요사항보고서(" 없는 제목(유상증자결정, 전환사채발행결정). API에 이 양식의 공시가 없음 | 949 | 데이터로 확인 (952건 중 943건이 비상장 E) |
| 정정본인데 원본이 수집 시작일 이전 | 286 | 데이터로 확인 (수집 기간 안에 앞선 원본이 없음) |
| API에 사건은 있으나 우리 정정본이 API 최종본보다 나중 | 100 | **추정**: API가 일부 정정을 반영하지 못함 (원문 미확인) |
| 원본이 우리에게 있는데 API에 해당 사건이 없음 | 8 | **원인 미확인**: API 누락이나 철회된 사건일 가능성 |

108건(100 + 8)도 제목은 모두 DART 정식 양식 이름(`주요사항보고서(유상증자결정)` 등)이라, **제목 분류 기준으로는 우리 판정이 맞다.** 다음 단계에서 정정본 연결과 철회 처리를 만들 때 테스트 사례로 쓴다.

## 6. 수집·분류 결과 (2023-04-16 ~ 2026-10-15)

| 항목 | 결과 |
|---|---|
| B001 전체 | 28,745건 (코스피 5,449 / 코스닥 14,865 / 코넥스 631 / 기타 7,800), 제목 217종 |
| 유상증자 | 7,553건 (분석 구간 6,714) |
| 유무상증자 | 170건 (분석 구간 116) |
| CB | 4,161건 (분석 구간 3,633) |
| 정정본 비율 | 유상증자·CB 11,884건 중 원본 37.4%, 기재정정 59.7%, 첨부정정 2.6%, 첨부추가 0.3%, 정정명령부과 6건 |
| 시장별 (유상증자·CB) | 코스피 1,580 / 코스닥 7,147 / 코넥스 423 / 기타 2,734 |

**생존 편향 규모**
- 기타(E)로 분류됐는데 종목코드가 있는 회사는 상장폐지 후보로 본다. 이런 회사의 유상증자·CB 공시는 다음과 같다.

| 종류 | 공시 (전체 / 분석 구간) | 회사 (전체 / 분석 구간) |
|---|---|---|
| 유상증자 | 922 / 750건 | 95 / 81곳 |
| CB | 336 / 197건 | 52 / 46곳 |

- 분석 구간 기준으로 코스피·코스닥 유상증자·CB 7,880건 대비 **약 12%** 규모다.
- `corp_cls`는 조회 시점의 회사 상태로 보인다. 그래서 상장 여부로 거를 때 이 회사들이 빠지지 않도록 주의해야 한다.

## 7. 알게 된 것

- 접수번호의 날짜와 공시일(`rcept_dt`)이 다를 수 있다. 예: 2026-09-11(금) 접수 → 공시일 2026-09-14(월). `available_date`는 공시일로 둔다(늦은 쪽이라 미래 데이터 누수 방지에 안전).
- 제목 앞 태그의 의미가 모두 같지는 않다. `[연장결정]`은 정정이 아니라 기간 연장이다 (지금은 none 공시에만 나와 영향 없음).
- "자기전환사채매도결정"은 분류상 none이 맞다. 하지만 CB 잔량 추적에서는 "잔량 증가" 이벤트로 써야 한다.

## 8. 다음 작업
